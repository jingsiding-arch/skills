# 飞书定稿样式基线

基于用户最终确认并手工调整后的飞书文档，后续默认按这套风格生成优化需求文档。

## 一、整体原则

- 默认生成的是**轻量优化方案**，不是大而全 PRD。
- 目标是：一眼能看懂、能评审、能落地、能测试。
- 保持结构稳定、标题固定、段落简短。
- 同层信息优先合并成“统一规则”或“小表”，不要拆成多条近义 bullet。
- 默认不写多余的分析过程、协作痕迹、问题定义、方案对比、影响范围、验收口径。
- 默认不写“原来的 / 优化后”对比，除非用户明确要求保留对照。

## 二、固定章节

最终飞书文档默认只保留以下顶层结构：

1. `需求背景`
2. `需求方案描述`
3. `测试用例`
4. `当前文档下的待确认项`

其中：

- `测试用例` 下固定保留：
  - `3.1 具体测试用例（思维导图）`

## 三、各章节写法

### 1. 需求背景

- 使用一个**克制的蓝色高亮块**承载。
- 默认只写 `3` 句话，每句话直接描述一个当前问题或能力缺口。
- 不写业务场景铺垫、影响分析、目标收束，也不写“当前场景：/ 当前问题：/ 本次优化目标：”这类标签。
- 若有效问题点不足 `3` 个，可以写 `2` 句；若超过 `3` 个，合并压缩为 `3` 句以内。
- 高亮块内不要使用 bullet、编号列表或分段小标题。

推荐句式：
- `现有/当前 + 对象 + 只支持/缺少/无法 + 具体场景或能力；`

推荐形态：
```md
<callout background-color="light-blue">
宿舍申办只支持按学生类别、学生年级划分，无法满足多校区分别管理申办批次的诉求；
审批流程只支持配置角色节点，无法把学生本人纳入“拍照确认已入住 / 已退宿”的流程；
财务审核发现缴费、退费或确认材料问题时，也缺少打回学生确认后再回到财务节点继续审核的闭环。
</callout>
```

### 2. 需求方案描述

默认必须按**页面维度**展开。

页面级标题结构严格参考用户确认的飞书文档：

```md
## 需求方案描述
### 2.1 页面名称 / 页面路径
#### 2.1.1 改动点一
#### 2.1.2 改动点二
#### 2.1.x 操作流程
#### 2.1.x 权限控制
```

如果有多个页面，则继续扩展为：

```md
### 2.2 页面名称 / 页面路径
#### 2.2.1 改动点一
#### 2.2.2 改动点二
#### 2.2.x 操作流程
#### 2.2.x 权限控制
```

每个页面至少保留 `1` 条实质改动说明。`操作流程` 和 `权限控制` 不为凑结构机械保留，只在确实影响理解、实现或测试时输出。

页面内容默认先判断轻重：若只是新增字段、补充单条匹配规则、按钮文案或轻量配置项，页面标题下直接用 `1-3` 条短 bullet 写完，不强制拆改动点小节、字段表、页面表现、规则口径。

轻量页面推荐形态：

```md
### 2.1 宿管 > 【宿舍申办】 > 【宿舍申办批次】
- 新增：在「学生类别」、「学生年级」所在区域附近新增「校区」设置项（非必填），「校区」未选择时可展示为“全部”/空。
- 学生匹配申办批次时，统一按「学生类别」+「学生年级」+「校区」+「申请时间」+「启用状态」判断；「校区」为空表示该批次不限制校区。
```

当页面存在多个较复杂改动、跨状态流转或需要分别说明入口与规则时，再按**改动点**组织。推荐先识别每个页面的 `1-4` 个改动点，并用“动词 + 对象 + 结果”命名，例如：

- `新增人工确认筛选`
- `退宿入口移入详情并二次确认`
- `资格变动按名单口径提醒`

当同一页面存在 `2` 个及以上改动点时，可在页面标题下先放一张紧凑小表：

```md
| 改动点 | 用户要做什么 | 系统要保证什么 |
| --- | --- | --- |
| 新增人工确认筛选 | 辅导员快速定位待处理学生 | 名单口径与人工确认状态一致 |
```

随后直接按改动点展开正文。研发读完一个改动点后，应能同时知道入口在哪里、怎么操作、系统怎么算、异常怎么处理。

默认不写“兼容存量 / 保持原样 / 旧数据继续生效 / 空值不触发必填校验 / 未配置则按原逻辑执行”这类系统默认行为，除非它本身是评审争议点或会改变现有默认逻辑。

如果页面属于审核、审批、待办、确认等通常带移动端的功能，页面级标题默认同时标记端别：

```md
### 2.2 学籍异动审核（PC） / 学籍异动审批（移动端）
```

若移动端页面名未确认，正文标题只写已确认的 PC 页面或泛称“移动端审批”，具体移动端页面名放到底部待确认项，不在标题里写“待确认”：

```md
### 2.2 学籍异动审核（PC） / 移动端审批
```

改动点小节职责：

#### 页面表现

- 写页面展示、入口位置、按钮状态、弹窗内容、提示语、交互动作。
- 优先描述用户最终会看到和操作到的内容。
- 每个改动点下只写与该改动直接相关的页面表现。
- 默认控制为 `1-3` 条短 bullet，或 `1` 张紧凑小表（如 `场景 | 页面表现 | 备注`）+ `0-2` 条补充 bullet。
- 默认不要把同一条展示规则拆成“显示什么”和“不显示什么”两句重复写；如果后一句只是前一句的自然反面，保留前一句即可。
- 对学生端展示、老师端可见范围、按钮显隐等场景，优先用一条统一规则表达，不再把自然可推导的反面情况逐条展开。
- 当状态、提示文案、按钮状态达到 `3` 项及以上时，优先改成状态小表，不要先写状态列表、再写文案列表、再写按钮限制列表。
- 凡涉及字段填写、表单录入、配置维护，必须把字段口径写清：
  - 至少标记 `是否必填`
  - 已知时标记 `默认值`
  - 推荐写法：`字段名（必填，默认值：当天）`
  - 默认值未知但很关键时，不在正文写 `待确认`，把默认值问题放到底部待确认项
- 字段较多时，可直接改成简表：
  - `字段 | 是否必填 | 默认值 | 说明`
- 若已经用表格表达清楚，默认不要再用 bullet 重复同一信息。

#### 规则口径

- 写业务规则、执行口径、判定条件、批量处理逻辑、异常跳过逻辑。
- 条理上优先放“开关开启后 / 开关关闭后 / 特殊情况”。
- 默认控制在 `3` 条核心规则以内；若天然属于状态流转或分支处理，优先改成 `场景 | 触发条件 | 系统处理` 小表。
- 同一条规则只放在一个最合适的改动点小节里，不要跨改动点重复。
- 对“展示 / 不展示”“可选 / 不可选”这类口径，优先保留一条统一准入规则，不再机械列出它的正反两面。

#### 操作流程

- 仅当需求涉及跨页面跳转、跨角色协同、跨状态流转、审批链路变化、批量处理链路、异常分支或回退路径时输出。
- 先用 1 句简短说明流程。
- 需要输出时默认使用**飞书白板流程图**或流程图组件。
- 正确完成标准是：
  - 文档中实际插入了 whiteboard / 流程图组件
  - 组件内已写入流程图内容
  - 不是只在正文里保留一句流程说明
- 不再用长编号列表代替最终流程展示，除非用户明确说不要流程图，或当前环境无法创建白板并已说明原因。无法落图时保留 Mermaid 草稿或 `流程图待落白板` 标记，不能声称已经插入白板。

#### 权限控制

- 仅当本次新增按钮/入口/操作能力、改变可见范围/可操作范围，或角色边界影响实现与测试时输出。
- 只写该页面按钮或入口相关权限。
- 不写全模块权限矩阵。

## 四、测试用例写法

### 3.1 具体测试用例（思维导图）

- 不再写其他测试小节。
- 最终飞书文档中必须落成**可视化思维导图 whiteboard / 白板组件**，不得只用缩进 bullet、编号列表或普通文本树代替。
- 源 Markdown 可先按 `主链路 / 关键分支 / 异常场景 / 边界操作 -> 场景 -> 操作步骤 / 预期结果` 组织，创建飞书文档时必须转换为 Mermaid mindmap 并上传 whiteboard。
- 思维导图中的「操作步骤」必须按 `1. / 2. / 3. / 4.` 标序号，并沿同一条操作路径逐级向后延伸；不得把所有步骤并列放在同一个「操作步骤」节点下。
- 若某一步存在条件选择，条件必须从对应步骤节点分叉，每个条件分支下面再延伸各自的后续步骤和预期结果。
- 同一条业务规则默认只保留一条最具代表性的测试路径，不把自然反面、同义改写、仅换个说法的场景拆成多条近义测试。
- 若多条路径最终都在验证同一条规则，优先合并为更高抽象的分支树，而不是拆成多张表。
- 若 whiteboard 插入或上传失败，正文只保留 Mermaid `mindmap` 草稿和 `测试用例思维导图待落白板` 标记，并在交付回执说明降级原因。

## 五、待确认项写法

- 顶层标题固定为：`当前文档下的待确认项`
- 只保留真正还没定的 1-3 条问题。
- 不要把已经确认的内容继续留在待确认项里。
- 所有正文中暂不确定的默认值、文案、数据口径、权限过滤、流程范围，都只放在本节，不要在正文里写“待确认”。

## 六、默认排版要求

- 允许轻美化，但必须克制。
- 推荐：
  - `需求背景` 用蓝色高亮块
  - 必要时用分割线分隔大章节
  - `测试用例` 用飞书白板思维导图组件
  - 需要展开 `操作流程` 时用白板流程图
  - 重点关键词允许少量加粗
  - 如需颜色强化，仅使用蓝色、紫色两色
- 飞书兼容性安全规则：
  - 不使用 `> - xxx`、`> 1. xxx` 这类 `blockquote + list` 组合
  - 不嵌套 `callout`
  - 如果正文已手写 `callout`，创建文档时优先用更保守的参数，避免自动美化再套一层高亮块

- 重点样式建议：
  - 开关名、模块名、字段标签、端别标记可优先 `**加粗**`
  - 对正文里承担“小标题”作用的冒号前短标签，可用蓝色或紫色 + 加粗做轻量强调；但 `需求背景` 默认不使用标签前缀
  - 若当前写入路径颜色稳定，可对少量标签使用蓝色或紫色
  - 不要整段大面积着色，不要把整个列表染色
  - 高亮块默认只保留背景色即可，不强制添加边框线颜色；如无特殊需要，优先写成 `<callout background-color="light-blue">`

### 标点语义规范

- `【】` 用于模块、页面、功能入口、较大的业务对象，例如：【宿舍申办】、【宿舍申办批次】、【宿舍申办审核】。
- `「」` 用于设置项、字段标签、按钮、操作项、状态项，例如：「校区」、「打回」、「拍照上传」、「必须上传」。
- `“”` 用于字段值、展示文案、枚举值、提示文案，例如：“全部”、“不显示 / 可上传 / 必须上传”、“待学生确认”。
- 表单里的字段名 / 字段标签默认使用 `「」`，不要用 `“”`；`“”` 只用于字段取值或页面展示出来的具体文案。
- 页面路径标题中可对核心模块或页面使用 `【】`，但不要把每个层级都机械加括号。
- 推荐写法：`在【宿舍申办批次】中新增「校区」设置项；「校区」未选择时展示为“全部”。`

- 默认不要：
  - 顶部导读
  - 阅读导航
  - 结构导图
  - 来源代码块
  - 截图占位
  - 大段 AI 解释文字
- 单个页面标题下的非表格正文默认不超过 `6-8` 条；超出时优先合并、转小表或拆分功能块，不继续加长列表。
