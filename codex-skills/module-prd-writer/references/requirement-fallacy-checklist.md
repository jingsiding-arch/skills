# 需求谬误与闭环断点检查清单

## 1. 目标谬误
- 需求动作是否真的服务于目标，还是把“管理诉求/汇报诉求”误写成产品功能？
- 业务目标、成功指标、验收标准是否同向，是否存在“目标是提效，方案却明显增负”的冲突？
- 一期范围是否足以独立产生业务价值，还是依赖二期/外部系统才能成立？

## 2. 责任断点
- 主流程里是否同时存在 `发起人`、`执行人`、`最终确认人`、`异常兜底人`？
- 异常、超时、撤销、补录、申诉分别由谁处理，是否存在责任真空？
- 是否存在“角色有动作但没权限”或“角色有权限但流程中没有承担动作”的矛盾？

## 3. 数据断点
- 核心对象是否有明确来源系统和唯一口径，例如名单、课表、记录、审批单、统计报表？
- 哪些字段允许人工修改，哪些字段由系统计算；两者冲突时以谁为准？
- 统计口径、日志留痕、导出结果、消息通知中的数据是否一致？

## 4. 流程断点
- 主流程是否有明确起点、终点、关键节点、状态变化？
- 每个状态是否都有入口和出口，是否存在“只能进入不能退出”或“无触发条件自动跳转”的状态？
- 失败后是否定义了回退、重试、超时、人工介入、恢复执行的方式？

## 5. 规则谬误
- 每条高影响规则是否写清 `判断主体`、`触发时点`、`阈值/条件`、`数据来源`、`执行动作`？
- 是否存在互相冲突的规则，例如请假优先级与缺勤统计口径相互打架？
- 是否存在制度上成立、系统上无法判断或无法执行的规则？

## 6. 依赖断点
- 上游/下游系统是否真实存在，是否已经具备对接条件，而不是想象中的能力？
- 如果依赖暂时不可用，是否有人工兜底、降级方案或灰度方案？
- 是否把其他模块的问题错误地塞进当前模块，导致本次交付边界失控？

## 7. 验收断点
- 是否能明确说出“什么情况下算上线可用”，还是只有抽象目标没有可验收标准？
- 是否存在必须依赖 `TBD` 才能验收的核心场景？
- 业务、研发、测试、设计是否都能找到自己需要确认的内容？

## 8. 输出分级建议
- `致命断点`：会直接阻断核心流程闭环、导致无法验收、依赖不存在能力或出现责任真空的问题。
- `高风险假设`：可以先按假设继续写，但一旦假设不成立，就会明显影响方案正确性、排期或验收的问题。
- `优化建议`：不影响当前版本闭环，但会影响体验、效率、扩展性或后续运营效果的问题。
