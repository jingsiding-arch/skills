# 开发工作量评估与 Base 甘特图

当用户在 PRD 之外还关心工期、里程碑、版本节奏、研发排期或甘特图时，按本文件执行。

## 1. 什么时候必须补排期

- 用户明确说要工期评估、开发计划、里程碑、版本计划、甘特图。
- 用户给了“本月底上线”“两周交付”“下个冲刺完成”这类明确时间要求。
- 当前输出已经是研发开发版，且用户希望研发可直接开工。

## 2. 最小输入

至少补齐这些信息：

- `project_name`：项目或模块名称
- `required_end_date` 或用户给出的工期要求
- `tasks[]`：至少按模块拆开的关键任务

如果用户没有明确开始日期，可默认写为“下一个工作日 10:00”，但必须在回复里说明是假设。

## 3. 工作量估算口径

默认用“人天”表达，不要混用“自然日”和“人天”。

推荐拆法：

- 纯配置/纯字段/纯列表微调：`0.5-2` 人天
- 常规列表页 + 筛选 + 详情/表单：`2-4` 人天
- 含状态流转、复杂校验、批量操作：`3-6` 人天
- 含跨系统依赖、审批/规则引擎、复杂联动：`4-8` 人天
- 联调、回归、验收支持：单独拆任务，不要塞进主开发任务

常见加权项：

- 新接口或接口重构：`+1-3` 人天
- 权限/数据隔离：`+0.5-2` 人天
- 通知/日志/导出：`+0.5-1.5` 人天
- 历史数据迁移或兼容：`+1-3` 人天
- 高风险外部依赖：单独列风险，不要假装零成本

## 4. 排期输出要求

至少要有两层：

1. 回复正文里的工作量评估表
2. 给脚本消费的结构化 JSON 计划

正文表最少字段：

| 模块 | 关键任务 | 责任角色 | 工作量(人天) | 计划开始 | 计划结束 | 前置依赖 | 风险备注 |
| --- | --- | --- | --- | --- | --- | --- | --- |

## 5. JSON 计划格式

```json
{
  "project_name": "课堂考勤模块一期",
  "start_date": "2026-04-21",
  "required_end_date": "2026-05-09",
  "tasks": [
    {
      "module": "公共配置",
      "task_name": "配置页与规则校验",
      "owner_role": "前后端",
      "stage": "开发",
      "priority": "P0",
      "effort_days": 3.5,
      "start_date": "2026-04-21",
      "end_date": "2026-04-24",
      "parallel_group": "A",
      "predecessors": "无",
      "deliverable": "完成配置字段、保存和启用校验",
      "risk": "依赖组织主数据"
    }
  ]
}
```

约束：

- `tasks` 不能为空
- 每个任务都必须有 `module`、`task_name`、`effort_days`、`start_date`、`end_date`
- 日期允许写 `YYYY-MM-DD` 或 `YYYY-MM-DD HH:mm:ss`
- 同一个模块可以拆多个任务，不要把整模块压成一行

## 6. Base 生成方式

优先使用：

```bash
python3 scripts/create_lark_dev_gantt.py --plan "/absolute/path/to/dev-gantt-plan.json" --dry-run
```

确认结果后再真实执行：

```bash
python3 scripts/create_lark_dev_gantt.py --plan "/absolute/path/to/dev-gantt-plan.json"
```

脚本默认会：

- 校验结构化计划
- 生成开发排期表
- 创建 `gantt` 视图
- 将 `计划开始` / `计划结束` / `任务名称` 绑定到甘特图时间轴

## 7. 回复口径

回复里不要只贴 Base 链接。至少同时说清：

- 总工作量
- 关键路径
- 是否满足工期
- 如果不满足，建议压缩范围、增加并行或拆版本
