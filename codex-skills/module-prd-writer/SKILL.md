# Module PRD Writer

默认输出中文。默认交付 **评审兼落地版 PRD**。

核心标准只有一句话：

> 研发和测试拿到文档后，应能直接拆任务、写接口、写测试点，而不是继续猜你意思。

## 表达收敛规则

- 默认优先写**短标签句**，不要把同一意思在“本轮更新 / 本轮关闭的问题 / 本轮修订点”里重复说三遍。
- 若同一信息已经在模块开头写过，就不要在紧随其后的“页面说明”里再重复一遍同义句；只补新增信息。
- 若一句话能说明白，不要展开成三句同义改写。
- 研发交付版的重点是**规则、边界、字段、动作、异常**，不是文风铺陈。
- 默认 PRD 目标是：**一眼能扫结构，研发能抓重点，测试能找验收**；不是把所有可想到的章节、表格、边界全部摊开。
- 同一页面 / 模块下，如果多张表最终都在描述同一组对象，优先合并为一张“字段 / 动作 / 规则 / 验收”小表，不要拆成多张近义表。
- 任意模块小节默认先写“页面定位 / 使用角色 / 前置条件 / 核心规则摘要”四个短标签；除非确实需要，不再额外写长段背景。
- 任意表格默认控制在 `3-6` 行；超过时优先保留 P0 字段、P0 按钮、P0 规则，其余写入“后续字段补全 / 附表待补”，不要把首版正文堆成字段大全。
- 任意单个模块默认最多保留 `3` 张核心表：字段/配置表、动作/按钮表、规则/验收表；只有用户明确要“研发开发版全量字段”时，才拆成更多表。
- 面向飞书定稿时，模块开头与页面说明里的短标签句优先写成：
  - `<text color="blue">**页面定位**</text>：...`
  - `<text color="blue">**使用角色**</text>：...`
  - `<text color="blue">**前置条件**</text>：...`
- 若当前只输出本地纯 Markdown、尚未面向飞书，可退化为：
  - `**页面定位**：...`
  - `**使用角色**：...`
  - `**前置条件**：...`

## 飞书工具规则

- 遇到 `*.feishu.cn` / `*.larksuite.com` / 飞书云文档相关任务，优先使用 `lark-cli`。
- 需要把本地 Markdown 沉淀为飞书 PRD 文档时，默认优先使用 `lark-md-pretty-doc` 对应的创建脚本，不要直接手写大段 `lark-cli docs +create --markdown ...`。
- 对已有飞书 PRD 文档的创建、整篇替换或追加更新，优先使用 `scripts/sync_lark_module_prd_doc.py`，不要在回复里只说“建议同步到飞书”。
- 创建或更新飞书文档前，必须先做飞书预检：
  - 先执行 `lark-cli doctor`
  - 若使用 `--as user`，再执行 `lark-cli auth status`
  - 任一步失败时，必须先走飞书配置/认证流程，不得假装“已生成飞书文档”
- 若用户未指定飞书目标位置，默认将新文档创建到个人知识库 `my_library`，不要因为没给 `folder-token` 或 `wiki-node` 就停住。
- 调用创建或同步脚本前，默认先执行一次 `--dry-run`，确认：
  - 飞书预检是否通过
  - 最终落点是否正确
  - 若源文档已含 `<callout ...>`，最终创建参数是否应降级为更保守模式
- 生成给飞书消费的 Markdown 时，优先使用飞书兼容性更稳定的语法，不要为了样式感使用高风险组合写法。
- 明确禁止以下易导致飞书丢内容或渲染空块的写法：
  - `> - xxx`、`> 1. xxx` 这类 `blockquote + list` 组合
  - 在 `callout` 中再嵌套 `callout`
  - 依赖本地 Markdown 预览成立、但飞书不稳定的复杂混合块级语法

## 本 skill 的新增强约束（高优先级）

如果用户明确说：

- “研发交付版”
- “给研发开发/测试验收”
- “补细一点”
- “按模块写”
- “把字段、筛选、按钮写出来”

则**功能需求明细不能只写总表**，必须改为：

> **按模块展开描述**，且每个模块都要包含该模块真实存在的页面元素、功能按钮、业务规则、页面与交互要求等；不要为不存在的筛选区或列表区硬凑表格。

新增约束：

- **统计页面和常规列表页面不是同一种页面模型**
- 对统计页、看板页、趋势页、汇总页、驾驶舱页，不要机械要求“列表字段定义表”
- 这类页面即使存在图表下钻、排行、卡片区、汇总区，也应优先写：
  - 统计视图说明
  - 指标卡/图表/趋势区定义
  - 口径说明区
  - 下钻动作/导出动作
  - 状态提示与刷新边界
- 只有当统计页里真实存在一个独立、稳定、可配置列的列表/台账区域时，才补“列表字段定义表”

也就是说：

- 不能只写一张跨模块总表就结束。
- 不能只写“支持筛选/支持列表/支持编辑”。
- 不能只写“展示基础信息/常用字段/常用操作”。
- 必须把用户真正会看到的**筛选项名、字段名、按钮名、状态名**写出来。

## 输出模式偏好（三模式）

根据用户目标，优先选择以下三种输出风格之一：

### 1. 评审讨论版

适用：
- 用户主要想梳理业务
- 想发现漏洞、冲突、闭环问题
- 想先开会评审

特点：
- 更强调背景、目标、范围、流程、漏洞和待确认问题
- 仍然保留关键工程信息，但可以简化字段和规则展开深度
- 适合拿去讨论，不要求一次写到研发直接开工
- 默认只保留 `背景与目标`、`范围边界`、`角色权限`、`主流程与异常`、`模块拆解`、`待确认项`。
- 功能明细只写关键页面和关键规则，不输出全量字段表；如需字段，最多给 `1` 张关键字段/按钮/规则合并表。

### 2. 研发开发版

适用：
- 用户明确说这份 PRD 主要给研发开发和测试验收用
- 需要直接支持拆任务、写接口、写测试点
- 需要按模块展开字段、筛选、按钮、规则和交互

特点：
- **必须按模块展开功能需求**
- **必须补齐字段、筛选项、列表字段、按钮、规则、交互、状态异常、验收口径**
- 不能只停留在业务评审层
- 允许比评审版更完整，但仍要表格合并优先：默认每个模块最多 `4` 张表，除非用户明确要求“字段全量展开 / 逐字段补齐 / 完整开发稿”。
- 若同一页面字段超过 `8` 个，正文先写核心字段，剩余字段独立成“字段补充表 / 附录”，不要塞在主链路说明里。
- 测试验收默认与规则表合并为 `规则 / 触发条件 / 处理口径 / 验收点`，不要再额外重复写一张总体验收表，除非验收口径跨模块。

### 3. 评审兼落地版（默认）

适用：
- 用户既想梳理业务，也希望研发后续能接得住

特点：
- 先保证业务与评审逻辑完整
- 再把关键规则写到工程可落地程度
- 若模块较复杂，也应优先采用“按模块展开”的写法
- 默认采用**精简落地稿**：保留研发最关心的字段、按钮、规则、异常，但不追求全量字段大全。
- 默认每个模块输出 `1` 段短标签说明 + `2-3` 张核心表；没有真实价值的表格直接删除。

如果用户没有明确指定，默认使用 **评审兼落地版**。
如果用户明确说“先出评审稿/先讨论”，优先用 **评审讨论版**。
如果用户明确说“给研发开发/测试验收/研发交付版/按模块写细”，优先用 **研发开发版**。

## 先判断场景

### 场景 A：信息很少

例如只有一句模块名。

输出：

1. 当前已知信息
2. 关键缺口 / 明显冲突
3. 1-3 个高价值澄清问题
4. 素材清单
5. PRD 目录骨架
6. 至少 1 个“模块级交付骨架”示例

不要假装已经能写完整开发版 PRD。

即使是骨架版，也不要只给空表头。

至少补一个**合并骨架表**，不要拆成一堆空表：

| 类型 | 示例项 | 说明 / 待确认 |
| --- | --- | --- |
| 筛选/字段 | 2-3 个贴近模块的示例项 | 可写 `TBD`，但字段名要具体 |
| 按钮/动作 | 2-3 个核心动作 | 说明触发条件或权限 |
| 规则/验收 | 2-3 条关键规则 | 同步写验收点 |

字段值可以写 `TBD`，但字段名和典型场景要尽量贴近该模块。

### 场景 B：信息不完整，但用户要“先出一版”

输出固定结构：

1. 已确认信息
2. 假设清单（含依据与风险）
3. PRD 草案正文
4. 候选方案（非结论）
5. 待确认问题
6. 按模块展开的关键字段 / 按钮 / 规则合并表（可含 `TBD`）

草案模式下，这些按模块表格**不能只有表头**，必须包含可推导的示例行；但默认用合并表，不要把草案写成完整开发手册。

### 场景 C：信息已足够

当已有：

- 范围边界
- 主要角色
- 至少 1 条主流程
- 至少 1 条异常规则
- 关键依赖或关键口径

则输出完整开发版 PRD。

### 场景 D：输入有直接冲突

例如：

- 一期不做移动端，但要求手机审批
- 配置项不可改，但又要求运行中动态切换
- 范围外不做审批流，但验收要求闭环审批

先输出：

1. 关键冲突/阻塞项
2. 为什么会卡住方案或验收
3. 建议决策（A/B）
4. 未决前可先写的章节
5. 必须保留 `TBD` 的章节

冲突前置，不要埋在文末风险里。

冲突模式下，除了业务结论，还必须补：

- 受影响模块
- 受影响页面/入口
- 受影响字段/筛选/按钮
- 受影响交互与触发逻辑
- 受影响生效规则
- 受影响配置可编辑边界
- 受影响验收项

### 场景 E：用户基于上一版补充修改

如果用户是在补已有 PRD，且明确要“继续改”或“补细”，优先输出：

- 本轮更新章节
- 本轮关闭的问题
- 本轮修订点
- **受影响模块的完整重写块**

不要只给“修改说明”，而不给完整可替换正文。

如果用户明确指出“功能需求明细不够细”“筛选项没写全”“字段没写出来”，或指出“某页面其实没有筛选/列表却被强行写了”，则必须：

- 重写受影响模块的完整小节
- 把筛选项、字段、按钮、业务规则、交互、验收都补齐
- 不允许只加几句说明

## 默认沉淀为飞书 PRD 文档

当用户使用本 skill 整理模块级 PRD 时，默认目标不是只停留在聊天稿或本地 Markdown，而是产出可分享、可继续修订的飞书 PRD 文档。

执行规则：

- 当信息已足够形成可评审 / 可研发交付版本时，默认直接创建或更新同一份飞书 PRD 文档，不再额外询问“是否生成飞书文档”。
- 若已有原飞书链接或文档 token，优先更新同一份文档；**默认采用整篇替换**，确保飞书正文与最新 Markdown 保持一致，而不是在文末不断堆叠历史版本。
- 若用户没有提供现成飞书链接，则默认新建一份飞书 PRD 文档；标题应基于模块主题、版本目标和日期自动生成。
- 若当前仍处于信息明显不足、关键决策未定的阶段，可先继续多轮收敛；一旦达到稳定版本，应在同轮或下一轮直接完成飞书沉淀。
- 若用户明确说“先不要生成飞书 / 只要本地稿 / 先看 Markdown”，才只输出本地文稿。
- 若飞书创建或更新失败，需继续给出本地 Markdown 定稿，并简要说明失败原因，不要因为飞书失败而中断 PRD 交付。
- 默认流程为：
  1. 先产出本地 Markdown 定稿
  2. 使用 `scripts/sync_lark_module_prd_doc.py --dry-run` 做飞书预检和动作确认
  3. 通过后继续执行真实创建或更新
- 对飞书版模块 PRD，默认保留完整 PRD 结构，不像轻量优化需求那样压缩成 3-5 个章节。
- 但“完整结构”不等于全章节全量展开；默认允许将相近章节合并，例如把 `状态 / 通知 / 日志` 合并，把 `风险 / 依赖 / 待确认` 合并，把 `规则 / 验收` 合并。
- 若用户要“研发开发版”，飞书正文必须完整保留按模块展开的字段表、按钮表、规则表、交互表和验收内容；不允许为了“飞书更简洁”而自动删减关键工程信息。

## 开发型 PRD 的硬要求

以下 9 类内容不能缺，但应按页面真实形态裁剪，不要机械套模板：

1. 模块目标与页面定位
2. 筛选项定义（仅当页面存在筛选区时）
3. 列表字段定义（仅当页面存在列表/台账/表格/卡片列表时）
4. 表单字段/配置项/详情字段定义（仅当页面以配置、表单、卡片详情为主时）
5. 功能按钮 / 行操作 / 批量操作
6. 业务规则
7. 交互与触发逻辑
8. 状态异常处理
9. 研发与测试验收口径

如果信息不足，也必须给出 **`TBD` 骨架版**，不能整块省略。

精简展开规则：

- 默认先判断这 9 类内容是否可以合并表达；能合并就不要拆成 9 个小节。
- 推荐合并方式：`字段 / 配置 / 展示`、`按钮 / 动作`、`规则 / 异常 / 验收` 三类核心表。
- `交互与触发逻辑` 只有在用户操作会引发跨页面、跨状态、跨角色或外部接口变化时单独成表；普通“点击保存 -> 保存成功”不单独成表。
- `状态异常处理` 与 `业务规则` 高度相关时，合并到规则表的“异常/失败处理”列里，不另起状态异常小节。
- `研发与测试验收口径` 默认并入规则表或按钮表的“验收点”列；只有跨模块验收、性能/并发/接口类验收才单独成章。

## 新增闭环：开发工作量评估与 Base 甘特图

当满足以下任一条件时，PRD 定稿后不能停在文档层，必须继续补上“开发排期交付”：

- 用户明确提到：`工期`、`排期`、`开发计划`、`研发节奏`、`里程碑`、`甘特图`
- 用户要求“给研发排期”“评估开发工作量”“按版本落计划”
- 当前输出是研发开发版，且用户已经给了明确时间要求、上线时间、冲刺周期或版本截止时间

强约束：

- 先产出 PRD，再产出模块工作量评估；不要倒过来先拍排期。
- 工作量评估必须按模块或模块内关键任务拆开，不能只给一句“预计 2 周”。

- Base 相关操作必须遵守 `lark-base` 和 `lark-shared` 规则；不要改走手写 OpenAPI。

### 5. 主流程与异常流程

主流程要写：

- 谁发起
- 谁执行
- 谁确认
- 谁兜底
- 状态如何流转

默认精简写法：
- 主流程控制在 `3-6` 步；超过时只保留主干，分支放异常流程表。
- 每一步只写 `角色 -> 动作 -> 结果`，不补背景解释。
- 低频分支、纯兜底说明、默认系统行为不要塞进主流程。

主流程默认要写成**容易被自动画图的步骤结构**：

- 优先用 `1. 2. 3.` 的编号步骤，不要写成长段散文
- 每一步只写一个关键动作，格式优先统一成：`角色 -> 动作 -> 结果`
- 若一步里既有系统动作又有人动作，拆成两步，不要塞进一句长复合句
- 流程步骤尽量使用稳定动词：`创建`、`提交`、`校验`、`生成`、`确认`、`驳回`、`关闭`、`通知`
- 避免在一步里堆太多“如果/但是/同时”；分支逻辑放到异常流程表，不要混进主流程
- 若后续要沉淀飞书，章节标题里优先显式包含 `流程` 或 `流转`，例如：
  - `### 5.1 主流程`
  - `#### 6.3.6 操作流程`
  - `### 9.1 状态流转`

不推荐写法：

- 一大段 6-10 行自然段描述整条流程
- 一步里同时出现 3 个以上并列动作
- 把正常链路和异常分支混写在同一条编号里

异常流程要写成表：

| 异常场景 | 触发条件 | 系统处理 | 人工处理 |
| --- | --- | --- | --- |

异常流程表也要服务于后续自动画图：

- `异常场景` 列优先使用短语，不要写成长句
- `触发条件` 只写触发判断，不展开背景说明
- `系统处理` 和 `人工处理` 各写一个主动作，避免一格里塞整段解释
- 若某异常是主流程中的高频分支，应确保它能和主流程某一步明确对应

## 细致度硬规则

### 1. 筛选项

只有页面真的存在筛选区时才写。

不要写：

- 支持按状态、时间等筛选
- 支持常用筛选项

必须写清：

- 具体筛选项名
- 控件类型
- 数据来源
- 默认值
- 是否多选
- 联动规则

例如不要只写“支持按状态筛选”，而要写：

- 学年学期
- 院系
- 专业
- 班级
- 课程名称/课程编号
- 日期范围
- 任务状态
- 确认状态
- 考勤方式
- 负责人

如果页面没有筛选区，例如公共设置、扫码页、蓝牙页、确认页，就不要硬写这一节。

### 2. 列表字段

只有页面真的存在列表/台账/表格/卡片列表时才写。

不要写：

- 展示基础字段
- 展示业务信息
- 展示常用列

必须写清：

- 字段格式
- 字段名
- 数据来源
- 是否排序
- 空值展示

例如不要只写“展示任务信息”，而要写：

- 任务编号
- 课程名称
- 课程编号
- 教学班
- 上课日期
- 节次
- 考勤方式
- 负责人
- 任务状态
- 确认状态
- 更新时间

### 3. 表单字段 / 配置项 / 详情字段

对于配置页、创建页、编辑页、详情页、确认页，优先写这类字段表，而不是“页面元素定义表”。

必须写清：

- 分组/区域
- 字段名
- 字段类型
- 数据来源
- 展示/输入方式
- 默认值
- 说明或校验规则

如果页面是“列表页 -> 创建页/编辑页 -> 详情页”的结构，则要把跳转后的页面字段单独写清。

### 4. 功能按钮 / 操作

不要只写：

- 支持新增/编辑/保存/启用/导出

必须写清：

- 按钮名 / 操作名
- 所在位置（页面顶部 / 行操作 / 批量操作 / 详情页）
- 触发条件
- 权限
- 是否要二次确认
- 是否要填写备注
- 成功结果
- 失败处理

### 5. 交互逻辑

必须写清：

- 页面/入口
- 用户操作
- 前端反馈
- 后端逻辑
- 成功结果
- 失败处理

即使是冲突场景，也必须写“受影响的交互”。

### 6. 生效规则

必须回答：

1. 全局还是局部
2. 在谁身上生效
3. 在哪里生效
4. 何时生效
5. 是否追溯历史
6. 冲突时谁优先

若是局部生效，必须说明按哪一层生效：

- 批次
- 学校
- 班级
- 课程
- 角色

### 7. 配置边界

必须回答：

1. 草稿态能不能改
2. 生效后能不能改
3. 使用中能不能改
4. 改后影响什么
5. 为什么限制

如果用户提到“改配置会影响使用中的逻辑/线上bug”，必须说明：

- 影响哪些功能
- 是否影响进行中的业务
- 是否只影响新数据

### 8. 异常与边界

至少覆盖：

- 主流程失败
- 外部依赖失败
- 配置变更影响进行中业务
- 状态冲突
- 回退或兜底

### 9. 验收标准

不要只写：

- 功能可正常使用
- 页面展示正确

必须写到：

- 什么条件下通过
- 什么边界条件必须验证
- 是否要黑盒 / 白盒 / 接口断言 / 时序测试 / 并发测试

## 按模块内嵌表格，不再单独输出“工程附表”章节

如果按模块写，则以下表格按需写在模块小节中：

- 若有筛选区：筛选项定义表
- 若有列表/台账：列表字段定义表
- 若是统计/看板/趋势/汇总页：优先写统计视图说明、指标卡/图表定义、口径说明、下钻与导出动作；不默认写列表字段定义表
- 若是配置/表单/详情页：配置项定义表 / 表单字段定义表 / 详情字段定义表
- 功能按钮 / 行操作 / 批量操作表
- 业务规则表
- 关键交互与触发逻辑表

默认不要在文末再重复汇总一套同义表格，除非用户明确要求输出“汇总表”。

## 关键原则

- 能按模块写，就不要只给总表
- 能写具体字段，就不要只写概念
- 能写具体筛选项，就不要只写“支持筛选”
- 能写具体按钮，就不要只写“支持新增/编辑”
- 用户给了工期或要求甘特图时，PRD 完成后还要继续完成排期与 Base 甘特图，不要停在文档交付
- 信息不足也要输出开发骨架
- 没有证据时写 `TBD`，不要伪造
- 对用户举的具体例子，必须翻译成可开发规则，而不是只复述
- 对复杂场景优先补“受影响模块完整交付块”，不要只补业务说明
